# 직접 질문과 필요한 정보 조회

사용자는 기업을 먼저 선택하지 않고 채팅에 질문한다. Agent가 질문과 최근 대화를 해석한 뒤 필요한 기업 정보나 법령을 조회한다. 답변은 조회 근거를 사용한다. 대상이나 판단 조건을 정할 수 없을 때만 추가로 묻는다.

Agent 실행 응답은 [Generation HTTP v0.3](agent-generation.md)을 사용한다. 기본 실행의 회원 인증과 CSRF는 [회원 계약](membership.md)을 따른다. 대화 저장과 목록 및 이어하기는 [이력 v0.4](history.md)를 따른다. 선택 기업 문맥은 필수가 아니다.

## 처리 기준

| 질문이나 조회 결과 | 처리 |
| --- | --- |
| 부산 협력사 찾아줘 | 지역 조건으로 기업을 검색한다. 공정은 필수가 아니다 |
| 해솔정밀에 대해 알려줘 | 기업명을 조회한다. 유일한 기업이면 상세 정보를 이어서 조회한다 |
| 부분 이름에 여러 기업이 일치 | 확인된 기업 이름과 ID를 선택지로 제시한다. 임의로 첫 기업을 고르지 않는다 |
| 결제 90일로 해도 돼? | 관련 법령을 검색한다. 숫자가 있다는 이유로 RFQ와 단가를 요구하지 않는다 |
| 하도급법상 대금 지급 기한은? | 법령 검색과 필요한 조문 조회를 실행한다. 조문 번호를 사용자에게 요구하지 않는다 |
| RFQ가 뭐야? | 기업 정보나 법적 수치를 만들지 않고 개념을 설명한다 |
| 이 회사의 재무 상태를 알려줘 | 질문과 최근 대화 및 선택 문맥에서 기업을 찾는다. 찾을 수 없을 때만 기업을 묻는다 |
| 특정 거래의 협상안 전체 검사를 명시했지만 필수 조건이 없음 | 도구 실행에 꼭 필요한 실제 거래 조건만 묻는다. 모르는 값을 채우지 않는다 |
| 정상 조회 결과가 0건 | 결과가 없다고 안내한다. 근거 없이 답변을 생성하지 않는다 |
| 도구 연결 실패 | 조회 실패를 안내한다. 사용자 정보가 부족한 것으로 처리하지 않는다 |
| 일부 근거 조회만 성공 | 확보한 근거로 답하고 확인하지 못한 부분을 구분한다 |

추가 질문에 대한 짧은 답변은 최근 대화의 원래 요청과 함께 해석한다. 예를 들어 재무 상태를 물은 뒤 기업을 묻는 답변이 나오면 사용자는 기업 이름이나 ID만 보내면 된다. 현재 질문 원문은 `decomposition.original_query`에 그대로 남긴다. 새 법령 질문처럼 주제가 바뀌면 이전 요청을 강제로 재개하지 않는다.

## 기업 조회

`supplier_search`는 주어진 공정과 소재 및 지역과 인증 등의 조건만 사용한다. 조건이 적어도 제한된 목록을 먼저 조회할 수 있다. `search_suppliers`의 기본 limit은 20이며 최대 100이다. 반환 순서를 구매 추천 순위로 해석하지 않는다. 특정 RFQ에 대한 순위는 `rank_suppliers`가 처리한다.

질문에서 기업 수를 지정해 `top_n`이 있으면 `distinct_suppliers=true`로 조회한다. 검색 조건을 만족하는 행 중 기업별 대표 행 하나를 선택한 뒤 limit을 적용한다. 같은 기업의 여러 공정이 기업 수에 중복 집계되지 않는다. 대표 행의 공정과 소재가 그 기업의 전체 생산능력을 의미하지는 않는다. 전체 상세 정보는 `get_supplier`로 조회한다. 기존 MCP 호출의 기본값은 false이며 공정별 행을 반환하는 동작을 유지한다. Generation의 검색 근거는 최대 10개이므로 큰 목록 전체를 보여주는 용도로 사용하지 않는다.

기업명으로 `supplier_detail`을 요청하면 business-mcp의 읽기 전용 `find_suppliers`를 먼저 호출한다.

```json
{
  "matches": [{"supplier_id": "SUP-0041", "name": "해솔정밀", "region": "부산"}],
  "total": 1,
  "match_type": "exact"
}
```

위 값은 가상 기업 예시다. `match_type`은 `id` 또는 `exact` 또는 `partial`이다. 정확한 이름 일치를 우선한다. `total`은 반환 제한 전 일치 기업 수다. 후보는 기본 10개만 반환한다. 유일한 후보의 ID로 `get_supplier`를 호출한다. 여러 후보를 구분할 때는 `answer.options`에 확인된 이름과 ID를 담는다. 예외 문자열에서 후보를 추출하지 않는다.

## 클라이언트 연결

기업을 선택하지 않은 상태의 대화 생성 요청이다.

```http
POST /api/conversations
Content-Type: application/json

{"context":{"selected_supplier_ids":[]}}
```

응답의 `conversation_id`로 메시지를 보낸다.

```http
POST /api/conversations/{conversation_id}/messages
Content-Type: application/json

{"query":"부산 협력사 찾아줘"}
```

기업 선택은 선택 사항이다. 메시지에 `context`를 넣으면 그 요청에 사용할 선택 문맥을 바꾼다. 빈 배열을 보내면 이전 선택을 해제한다. `context`를 생략하면 서버가 저장된 선택을 유지한다. 기업 필터를 바꾸거나 기업을 선택해도 기존 대화를 자동 삭제하지 않는다. 새 대화는 사용자의 명시적인 동작으로 시작한다.

화면은 `answer.text`와 `answer.citations` 및 `answer.options`를 표시한다. 본문에는 이미 notices가 반영되므로 같은 안내를 반복해서 붙이지 않는다. 인용 링크는 HTTP 또는 HTTPS URL만 연다. `NEEDS_INPUT`은 추가 입력으로 이어가고 `FAILED`는 정상 답변으로 저장하지 않는다. `mode=stub`인 답변은 테스트 응답으로 표시한다.

`mode=live`는 실제 모델과 MCP를 사용하는 실행 모드다. 일반 지식 질문이나 추가 질문에서는 도구를 호출하지 않을 수 있다. 실제 호출 여부는 `routing.outcomes[].calls`로 확인한다. 조회 데이터 전체가 실제 기업 자료라는 뜻은 아니다. business-mcp의 `source`와 재무 자료의 출처를 구분해 표시한다. 저장소의 seed에는 DART CSV와 가상 기업 및 가상 운영 자료가 함께 들어 있다. DART 기업의 생산능력과 품질 및 계약과 견적도 seed가 생성한 자료다. 법령은 저장된 인덱스와 조회 기준일을 사용한다. 실행할 때마다 외부에서 최신 자료를 수집하지 않는다.

재무 금액은 조회 근거의 값과 단위를 보존한다. 구조화된 `revenue`와 `operating_income` 등의 금액은 원 단위다. `revenue_eok`는 억원 단위다. Generation은 숫자와 금액 단위를 함께 검사하며 임의의 반올림이나 조 단위 환산을 허용하지 않는다. 근거와 맞지 않으면 재작성을 요청한다. 재시도 후에도 남는 값은 `[확인 필요]`로 표시한다. 이 검사는 모든 문장의 의미와 계산 및 법률 해석의 정확성을 보장하지 않는다.

법령 검색 결과의 항에 없는 내용을 조문 전문에서 확인했다면 전문의 인용을 사용한다. 정상 조회된 전문에 본문과 citation 및 HTTP(S) 출처 URL이 있어야 한다. 다른 항의 인용으로 대신 표시하지 않는다. 출처 조건을 충족하지 못한 참고 근거는 계속 인용할 수 없다.

## 자동 검증 예시

stub은 자연어 모델을 대신하는 범용 규칙 엔진이 아니다. 아래 문서화된 질문과 짧은 후속 답변만 지원한다. 실제 그래프와 Routing 및 Generation의 근거 검사는 실행하며 모델과 도구의 입출력만 고정 데이터로 대체한다. live 요청이 실패해도 stub으로 전환하지 않는다.

| 질문 | 확인 항목 |
| --- | --- |
| 협력사 목록 보여줘 | 기업 선택과 공정 조건 없이 조회 |
| 부산 협력사 찾아줘 | 지역만으로 조회 |
| 경남 협력사 찾아줘 | 직접 질문 전용 가상 기업 조회 |
| 제주 협력사 찾아줘 | 결과 없음 |
| 프레스 협력사 찾아줘 | 공정 조건 조회 |
| 해솔정밀에 대해 알려줘 | 정확한 이름 조회 후 상세 조회 |
| 해솔에 대해 알려줘 | 두 가상 후보 중 선택 요청 |
| 없는기업에 대해 알려줘 | 기업명 조회 결과 없음 |
| 하도급법상 대금 지급 기한은 며칠이야? | 법령 검색과 조문 근거 |
| 결제 90일로 해도 돼? | 불필요한 거래 정보 요구 없이 법령 조회 |
| 이 회사의 재무 상태를 알려줘 → SUP-0041 | 기업이 없는 요청의 추가 질문과 원래 재무 질문 재개 |
| RFQ가 뭐야? | 도구가 필요 없는 개념 질문 |

추가 질문의 응답으로 `해솔정밀 (SUP-0041)`처럼 반환된 선택지를 그대로 보낼 수도 있다. Spring이 실제 선택지 번호를 이력에 보존한 경우 `2번`이나 `두 번째`로 선택할 수도 있다. 기업 선택 문맥이 있는 기존 가상 기업 질문과 분해 fixture의 세 질문(`shared/fixtures/decomposition`의 01, 09, 11)도 유지한다. 다른 임의 질문은 stub에서 `400 VALIDATION_ERROR`다. 실제 자유 입력은 live 모드에서 실행한다.

기존 세 가상 기업은 [supplier-chat fixture](fixtures/supplier-chat.json)에 있다. 후보 구분 검증용 기업 한 곳은 [direct-chat fixture](fixtures/direct-chat.json)에 있다. 법령 stub은 저장된 routing fixture를 사용하며 최신 법령 조회 결과로 표시하지 않는다.
